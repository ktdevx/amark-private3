# Brief: parser-core

## Problem

Amark は拡張の組み合わせで CommonMark や GFM などの方言を表現する。そのためには、個々の構文を知らずに「登録された構文に解析を委ねる」パーサエンジンと、構文を登録するための拡張 API が必要である。

## Current State

`foundation` と `node-tree` が基盤と木を提供する想定。パーサに関するコードは存在しない。

## Desired Outcome

- 構文を 1 つも登録していないエンジンは、入力を段落とテキストだけの木にする
- ブロック構文とインライン構文を拡張として登録でき、登録した構文が解析に参加する
- 拡張の集合を方言としてまとめ、方言を指定してパースできる
- 入力を分割して与えるストリーミング供給と、一括パースの両方ができる
- 悪意ある入力に対しても解析時間が入力長に対して線形に近い範囲に収まる

## Approach

cmark と同じ 2 フェーズ構成（行単位のブロック解析 → インライン解析）を採用し、エンジンは「開いているブロックの継続判定」「新しいブロックの開始判定」「インラインの文字トリガーによるディスパッチ」「デリミタの後処理」といった枠組みだけを持つ。各構文はコールバック群（vtable）として登録する。エンジンが汎用に提供すべき仕組み（デリミタスタック、ブラケットスタック、参照定義テーブル、遅延継続行など）は、CommonMark を拡張として書けることを基準に決める。

## Scope

- **In**:
  - パーサオブジェクトの生成・破棄、入力の供給（分割供給と終了）、文書の取得
  - 行の前処理（改行の正規化、タブ展開の扱い、NUL 文字の置換など構文に依存しない部分）
  - ブロック解析の枠組みとブロック構文の登録 API（開始判定、継続判定、クローズ時処理、子の受け入れ可否、内容の取り扱い種別）
  - インライン解析の枠組みとインライン構文の登録 API（トリガー文字、解析コールバック、デリミタ処理、後処理）
  - 拡張の定義（構文・ノード種別をまとめる単位）、優先順位と競合の解決
  - 方言（拡張セット）の定義と組み立て
  - 解析オプション、ネスト深さなどの上限
- **Out**:
  - 個別の構文の実装（commonmark が所有。段落とテキストという最小のフォールバックだけを持つ）
  - レンダリング
  - ロスレス、ソースマップの完全な保持

## Boundary Candidates

- 入力供給と行処理
- ブロックフェーズのエンジン
- インラインフェーズのエンジン
- 拡張登録 API と方言定義
- 共有される解析中状態（参照定義、デリミタ、ブラケット）

## Out of Boundary

- CommonMark の文字クラス表や HTML エンティティ表など、特定構文のためのデータ
- GFM 固有の仕組み（ただし、テーブルのように「段落を後から別ブロックに置き換える」構文を拡張 API で表現できることは設計時に確認する）

## Upstream / Downstream

- **Upstream**: foundation、node-tree
- **Downstream**: commonmark、将来の gfm、サードパーティ拡張

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: node-tree（拡張ノード種別の登録と構文登録を 1 つの拡張として扱えること）、commonmark（エンジンと構文の責務境界。commonmark 実装中に本 spec の API を改訂する前提）、html-renderer / markdown-renderer（1 つの拡張が構文とレンダラフックをまとめて提供できる形にする）

## Constraints

- エンジン内に特定構文の名前による分岐を持たない
- 拡張 API は公開 API とし、ライブラリ本体の CommonMark 実装と外部の拡張が同じ API を使う
- 失敗は `foundation` の共通エラーコードで返す
- 入力は UTF-8 を前提とし、不正なバイト列の扱いを定義する
- コーディング規約は `.kiro/steering/roadmap.md` の Constraints を正とする
